# Business workflows

This document owns user operations and state transitions. [Product scope](product-scope.md) defines release boundaries; [transaction contracts](transaction-contracts.md) define money, locks and retries.

Use the [user journey index](critical-user-journeys.md) for stable journey IDs, actor-specific acceptance outcomes and coverage references. This document owns the detailed flows; [system capabilities](system-capabilities.md) records implementation boundaries. The sections below describe behavior, not a fresh verification result.

## 1. States and authority

Generic expansion targets: guest checkout remains the neutral default, with backend-enforced account-required configuration. Profiles do not alter purchase snapshots; email changes require verification. Rewards are disabled until configured and require verified identity linked at acceptance. Shipping dispatch and local-delivery dispatch consume stock once; recorded delivery completes fulfillment. Pickup completes at verified handoff. Quantity-based partial shipments are supported; order completion and reward release wait for every ordered unit to be delivered. Historical completed orders retain meaning with no reward backfill.

Reward programs optionally select direct category membership (an empty allowlist includes all merchandise); product-level reward exclusions always win. Activation uses UTC instants, start inclusive and end exclusive. Quote acceptance revalidates activation boundaries and category eligibility. Accepted orders retain their policy and eligibility when programs or categories change later.

An owner may resolve a reward funding-review flag only after every frozen original receipt again supports its accepted funding; another receipt cannot substitute for the corrected source. Record verified evidence, request identity and audit. Pending completed orders then release their supported earning. For issued rewards, restore only the cumulative entitlement reduced by actual component refunds: cancel associated debt first, preserve active holds, and compensate debt already recovered from later earnings without duplicate recovery. Restorations retain original reward provenance. No reward financial email is emitted by this operation.

Optional slots identify method/location or service area, local date/window and timezone. Capacity counts orders; quotas count variant units independently of global stock. Completed bookings consume their production window. Rescheduling acquires destination before releasing source under sorted locks; reductions cannot silently invalidate bookings. Reward pending/released/reversed states obey [transaction contracts](transaction-contracts.md). Feature configuration and neutral onboarding must pass browser acceptance before release; these contracts do not claim all milestones implemented.

| Dimension       | States and rules                                                                                                                    |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Order           | open -> confirmed -> completed; open/confirmed -> cancelled before shipment or pickup handoff                                       |
| Payment review  | not_required, pending, needs_correction, verified; evidence review does not create a receipt                                        |
| Payment balance | Derived from effective receipts and settled excess returns: no_payment_due, unpaid, underpaid, paid, overpaid                       |
| Fulfillment     | unfulfilled -> preparing -> ready_for_pickup -> fulfilled, or preparing -> shipped -> fulfilled; eligible cancellation -> cancelled |
| Refund/return   | Authorized amount and settlement progress shown separately; pending, sending, partially_settled, settled or correction_reduced      |

Staff can record actual receipts, confirm payment and fulfill orders. Owner-only operations include price changes, cancellation, refunds, receipt corrections and payout execution. Customers cannot verify receipts, set prices or cancel orders. Every private use case checks the permission matrix in [architecture](architecture-overview.md).

Preparation requires confirmation. Pickup handoff or manually recorded delivery atomically completes fulfillment and the order. Shipment and cancellation share the order lock and recheck prerequisites. Shipped/completed orders use refunds; refunds alone do not stop fulfillment. Cancelled/completed lifecycle is terminal, but receipt and payout reconciliation remains possible.

## 2. Cart, quote and order creation

Customers browse before choosing fulfillment. Preserve their owned cart across refresh and language changes. On checkout, validate positive quantities, availability, destinations, shipping rates, tax and pickup notice. Explain incompatible items without deleting them. Client prices are never authoritative.

Create a server quote bound to cart ID/revision, expiry and the relevant catalog/settings versions. It includes the full payable total, item and fulfillment snapshots, chosen payment method/account and terms. A quote contains no instructions to send money. Require explicit acceptance of changes to price, fulfillment or terms.

Initial quote lifetime is 15 minutes.

On submission, authorize the guest cart and acquire the cart lock. An exact successful retry returns the existing order. Otherwise require a matching, unexpired quote and revalidate current inputs; a material change returns a replacement quote for acceptance. In one transaction create the open order and immutable purchase snapshot, assign a display order number and a human-friendly checksummed short payment reference code (e.g. `SP-XXXX`, generated from Crockford Base32 with a check character and bounded collision retry), convert the cart, record the request identity and emit order.submitted. Enforce one order per source cart across request keys. A new purchase uses a new cart.

Only after commit display payment instructions, the stable order reference and short payment reference code, issue the scoped session token in an HTTP-only secure cookie (with `sessionStorage` retention as a client helper), and send the acknowledgment email. For a zero-total order, confirm in the creation transaction if fulfillment remains valid; no method or proof is required. If a request times out, query/retry the same operation and display the existing order. Never prompt a second payment because the response was lost.

The accepted order is independent of subsequent cart, price and configuration changes. Placement reserves tracked variant availability and applied credit atomically; optional slot limits join that transaction. Unfulfillable committed orders require audited cancellation or returns. A paused store blocks new order creation under the store lock but permits all existing-order work.

## 3. Payment and confirmation

Each order selects an external method/account for the remainder after applied store credit; installment schedules are not offered. Display clear transfer details, a 1-click copy button for the exact amount and payment reference code, and standard transfer QR codes where supported. Cash instructions require collection before confirmation and preparation. A payment-method rename or archive preserves the historical account and order instructions. Owners can stop displaying unsafe instructions with an audited notice and arrange cancellation; changing a method never silently redirects an accepted order's payment destination.

Payment evidence accepts JPEG, PNG and WebP files smaller than 5MB. Evidence uploads attach to an existing authorized order. Create an expiring private upload intent, upload directly to storage outside the database transaction, then validate/finalize the object reference by verifying allowed file size, declared MIME type, and file magic bytes (inspected via partial byte-range read `Range: bytes=0-2047` on the candidate object). Interrupted uploads can retry without creating an order or receipt. Expired intent cleanup must not delete finalized evidence. Payment evidence is not a receipt.

Presigned uploads target staging keys only. Finalization copies the staged bytes outside the database transaction to a new private server-only candidate key, then validates that candidate's size, MIME type and magic bytes via partial range read. The candidate is never overwritten and is not accessible to customers before finalization. Under the order/upload-intent locks, recheck authorization and expiry and attach the validated candidate exactly once. Competing retries return the winning evidence record. Downloads always use that immutable final key, never the staging key; later staging overwrites cannot change reviewed evidence. Cleanup marks intents expired under the same locks and deletes only staging or unattached candidate objects after excluding active finalizations and committed evidence references. Test overwrites during copying, validation and after finalization, plus cleanup/finalization races.

Staff verifies actual transfers or cash collection and records amount, currency, durable account, unique reference and actor. Cash uses an internally generated receipt number and durable collection request key. Exact retries reuse the record; a second physical payment needs a new receipt. Multiple actual receipts are allowed for reconciliation of mistakes. Staff must agree any underpayment resolution with the customer rather than automatically issuing another payment request. Drawer reconciliation detects duplicate entries under different keys.

Confirm only when net receipts exactly equal the payable total, evidence review is satisfied where required, no unsettled excess return or accounting hold exists, and fulfillment is valid. Recording a receipt remains possible when timing or a hold blocks confirmation. Confirmation freezes original receipt funding. Late extra receipts remain surplus and do not increase purchase value or refund entitlement.

For rejected evidence, show needs_correction, the reason and a correction deadline. New evidence returns to pending. At expiry alert staff once per revision; do not infer nonpayment or cancel automatically.

## 4. Unpaid orders and permitted changes

Open unpaid orders stay visible in the merchant queue. Manual review deadlines never release credit/stock/slot reservations automatically: an unrecorded transfer may have arrived. Owner cancellation releases active holds atomically. Provider expiration requires terminal provider reconciliation and explicit late-payment handling.

An owner may revise an open order's price only when no receipt has ever been recorded and no refund/return authorization exists. Preserve the old snapshot, reason and proposed new total. Suppress payment instructions while customer acceptance is pending; changed terms require acceptance through scoped order access. Keep one pending proposal and reject stale revisions. Withdrawal restores the prior agreed instructions. Any receipt arriving before acceptance invalidates the proposal and is reconciled against the last accepted purchase; it must not apply new terms automatically. Cash follows the same rule.

Once any receipt is recorded, changing price requires cancellation/refund and a separately accepted new order. No post-payment price-change return workflow exists. Confirmed purchase totals never change.

An address correction before shipment must revalidate eligibility. For an open unpaid order, changed cost follows the acceptance rule above. Once paid, allow only same-cost corrections within supported shipping rules, audit them and notify the customer; otherwise use cancellation/new purchase. Pickup rescheduling validates notice and availability, records customer agreement and notifies them. It never silently changes the price.

## 5. Fulfillment

Display payment and preparation deadlines separately. For pickup, calculate the review deadline from the chosen time minus minimum preparation notice in the location timezone. Alert staff once per schedule revision when overdue. Confirmation rechecks notice, including free orders; invalid timing requires an agreed reschedule or cancellation.

Staff prepares confirmed orders, prints packing slips, marks pickup ready, or records carrier/tracking and shipment. Tracking corrections retain old/new values and send an update. Without a carrier integration, staff explicitly records delivery to complete a shipped order. Do not infer delivery from a tracking number or elapsed time.

Pickup handoff requires staff to verify the recipient using the scoped order page presented by the customer, or owner-assisted identity verification when that access is unavailable. Record the verifying actor and handoff time; assisted handoff also records the verification basis without copying unnecessary identity documents. An order number or matching contact text alone is insufficient. A separate pickup code is not part of the first release.

Customers contact the store for cancellation. The owner cancels only before shipment/handoff. The UI distinguishes 'Refund money' from 'Cancel order and resolve funds' and shows whether fulfillment will continue before committing.

## 6. Refunds, excess returns and cancellation

Only original-source payouts are supported. The owner selects amount, purchased components where applicable and reason. Authorize under the order/receipt locks using remaining entitlement and per-receipt capacity. Pending authorizations reserve funds immediately. Captured credit restores original source provenance; external funds return to their original source. An unrelated transfer cannot fund a cash payout. Preserve original account/source references if a method is archived.

For transfers, distinguish the merchant's receiving account from the payer's return destination. Before claiming a payout, the owner verifies that destination against the original transaction's bank/provider evidence and records the evidence reference, verified destination, actor and time. Customer-provided details alone are insufficient. If the source cannot be verified or cannot receive a return, keep the obligation pending for owner resolution; do not substitute another destination. Bind each claim to an immutable verified destination revision and show it before sending. A destination correction requires new verification and cannot alter an unresolved or settled attempt. For cash, verify the original payer or their documented authorized recipient and retain the recipient acknowledgment at settlement.

For a confirmed order, purchase refunds cannot exceed the frozen purchased components or their effective original funding. A genuine overpayment is a separate excess return, never extra purchase entitlement. For an open order, use cancellation to return actual collected money; do not represent the unpaid requested total as a refundable amount.

Cancellation preserves settled transfers and existing authorizations. For an open order, authorize only remaining actual received funds not already allocated. For a confirmed order, authorize remaining purchase entitlement and separately return unallocated surplus. Store an actual-funds cancellation entitlement for open orders; zero funds create no refund row. Commit lifecycle, fulfillment cancellation, new obligations, audit and events together. Existing or new payouts stay actionable after cancellation.

Late receipts on a cancelled order create an original-source return for their unallocated funds in the same transaction; they do not reopen the purchase. A cancelled unpaid order that later receives $40 owes a separate $40 return.

Before physically sending money, the owner claims an allocation with a durable attempt ID and exact amount. A second sender is rejected. A timeout leaves sending/uncertain state; it never releases the claim. Reconcile the existing transfer or record verified no-transfer evidence before a new attempt. Partial transfers leave only the unpaid authorized remainder. Cash requires a disbursement number and recipient acknowledgment. Unique outgoing references and capacity checks apply to every refund and return. Workers never send money.

Ordinary refund/return authorizations cannot be withdrawn or reused. An uncertain attempt blocks cancellation or corrections until reconciled. A supported correction may reduce only unsupported unsent obligations as described below.

Verified partial payouts within the claim and remaining authorization are ordinary settlement. Record the exact amount using the canonical calculation. Close the attempt as reconciled only when evidence establishes that the remaining claimed amount is not still pending; otherwise keep it exclusive. Once closed, a new claim may cover the remaining authorization if no other hold applies. No discrepancy or write-off is required for a correctly settled partial payout.

If a physical payout has erroneous disbursement E > 0, exceeds its claim limit, or introduces new evidence for a closed attempt under the transaction contract, record an owner-only payout discrepancy instead of rejecting the evidence or declaring no transfer. Preserve the claimed amount/destination and append the actual amount, actual destination, unique transfer reference, evidence and actor/time. Hold the order against new payouts, cancellation, receipt corrections and fulfillment while the owner investigates; permit incoming receipts and reconciliation. A wrong-destination transfer does not settle the customer's obligation. A transfer to the verified source settles the allocation's remaining authorized obligation even when it exceeds the individual claim. The claim-limit breach is an operational discrepancy; only money beyond the obligation is erroneous disbursement. Record erroneous disbursements and evidenced recoveries separately from customer settlement, without inventing receipt corrections or increasing authorizations. Resolution requires a reviewed classification of all actual funds and reconciliation of affected attempts. A recovery or write-off decision is required only for E > 0; a claim-limit breach with E = 0 requires acknowledgment without a monetary loss entry; only then release that case's hold and permit a new claim if no other hold remains. A write-off does not erase the transfer or forgive the customer's refund entitlement. Subsequent recoveries append to the same case. Workers never resolve discrepancies or send replacement payouts.

Late evidence for a closed payout attempt places any unresolved replacement on the same allocation into reconciliation-required review, even if no excess money is yet recorded. Stop unsent replacements and obtain no-transfer evidence; keep already-sent or uncertain replacements exclusive until reconciled. Sender screens recheck actionability before displaying instructions. Review all affected transfers and remaining entitlement before releasing the case hold. Do not change the old claim or automatically initiate another payment. Follow the cross-attempt examples in the transaction contract.

## 7. Receipt corrections

The owner can correct an erroneous entry with evidence; returning money that never arrived is not a correction. Open a case and hold each affected order against new payouts, confirmation, price changes, cancellation and fulfillment. Allow recording real incoming receipts and reconciliation of existing payout attempts. Permit at most one open correction case per affected order. A duplicate involving two orders locks and holds both in deterministic order.

Dismiss a correct receipt with evidence and no monetary entry. To apply a correction, reconcile uncertain attempts, revalidate the case against current financial revisions and append a signed delta. Effective receipt amount cannot be negative. A duplicate void links the surviving receipt and preserves both original references. An increase must substantiate the original payment; a new payment is a new receipt.

Wrong receiving-account reassignment is deferred from the first release. Amount deltas and duplicate voids must not change a receipt's account, currency or reference identity, and staff must not void/recreate a payment to bypass that restriction. Before recording a receipt, the admin interface must present an explicit confirmation step showing the durable receiving account name and details, requiring staff verification against the actual transaction before committing. If an existing receipt has the wrong account, open an owner investigation and retain its hold; do not mark it repaired through an amount correction or authorize payouts based on the incorrect source. An account-reassignment design covering identity collisions, funding and historical payout verification is required before such a case can be repaired in the application.

Retain confirmed purchase snapshots and settled payouts. Recompute effective original funding, reduce only unsupported unsent allocations, and record any uncovered purchase or excess disbursement as merchant loss. Do not charge the customer automatically. Review and commit all deltas, allocation revisions, loss changes, audit and notifications atomically before releasing holds. Subsequent corrections create linked cases and re-evaluate existing dispositions; losses cannot be counted twice.

For cancelled orders, additional corrected funds not already consumed by effective obligations create supplemental original-source returns in that same transaction. Preserve the original cancellation entitlement. For open/confirmed orders, display newly uncovered surplus for ordinary return authorization. See [canonical calculations and examples](transaction-contracts.md).

## 8. Access recovery and customer communication

Email recovery exchange tokens expire after 24 hours or first use. The browser's scoped order session supports tracking and evidence upload. A lost/expired link can be recovered through a rate-limited email verification flow (enforced via reverse proxy and application in-memory token buckets) with generic responses. Exchange a single-use token for a bounded order session; do not consume tokens on passive email-link preview. Contact text and order number alone reveal no private details.

Email failures appear in the admin queue; they do not roll back an order. Customers with a valid session can still track it. Customers without session or working email need owner-assisted identity verification; staff must not disclose an order based only on a matching contact string. Use transactional templates and store support details; a general messaging inbox is deferred.

## 9. Customer accounts and order ownership

Journeys: C13–C16. Register → verify email → sign in → open account. Invalid credentials and verification/reset failures must explain the next action without granting private access. Customer registration grants no merchant membership. Request a forgotten-password email → open the reset link → choose a new password → sign in; authenticated customers can also change their password, update their profile and sign out. Self-service email changes remain deferred.

Create/edit/delete an owned address → select it at checkout → review the accepted address snapshot. Profile/address changes do not rewrite existing orders. Reject access to another customer's address or order even when its identifier is known.

Open account order history → search by exact reference → inspect an owned order. To claim a guest order, provide its private access proof while signed in with verified identity. A matching email or order reference alone is insufficient. If private access is lost, use section 8 recovery; do not attach ownership based on contact text.

## 10. Card payments, credit and rewards

Journeys: C17, C20–C21, M14–M15. Create the order before requesting external payment. For Stripe, open hosted checkout → complete/cancel payment → return to private order tracking. Redirect success is not settlement: reconcile verified durable provider evidence before treating payment as received. Failed, expired or interrupted checkout retains the order for reconciliation; never infer that a timeout proves no payment. Provider refunds retain original-source and reconciliation requirements. See the [capability limits](system-capabilities.md#capability-inventory) for provider acceptance conditions.

A verified customer reviews available/reserved credit → requests an eligible amount during checkout → accepts a quote showing credit and any external remainder. Placement reserves credit; confirmation captures it; eligible unpaid cancellation releases the hold. Credit is funding rather than a discount. Refunds compensate original credit source lots separately from external payouts. Owners issue credit with an audit reason and inspect/export the ledger; unreconciled credit is not spendable. Customer top-ups and transfers remain deferred.

When rewards are configured and identity/merchandise/funding qualify, preserve the accepted policy and funding snapshots → wait for all units to complete delivery/handoff → release eligible credit. Refunds can reverse rewards or create debt according to transaction contracts. Funding-review cases require owner investigation and the original-source repair rules in section 1; no automatic historical backfill or substitute receipt is allowed.

## 11. Fulfillment choices and physical returns

Journeys: C18, C22–C23, A12–A13. At checkout choose one enabled fulfillment method. Shipping validates destination/rate; pickup selects a configured location and eligible window where scheduling is required; local delivery validates its area and optional schedule. Unsupported areas, blackouts, insufficient preparation notice or exhausted capacity require a revised selection while preserving cart contents. Review the resulting total before acceptance.

Staff and owners inspect slots/capacity and variant quotas and reschedule eligible orders with customer agreement. Only owners configure capacity or variant quotas. Agreed rescheduling validates destination notice and capacity and acquires the destination before releasing the source; existing bookings cannot silently disappear when limits are reduced. Apply backend role checks to every scheduling mutation. Partial dispatch records quantities and remaining units; order completion waits for every unit's recorded delivery. Section 5 owns handoff and delivery verification.

An authorized customer opens an eligible fulfilled order → requests return quantities → staff or owner reviews and approves eligible quantities → receives goods as restockable or damaged. Reject quantities exceeding remaining purchased eligibility. Receipt of goods changes stock independently of refund authorization. The owner separately authorizes any purchase refund and reconciles its settlement under section 6. Show request, approval, goods receipt, authorized refund and settled money as distinct progress; rejection or a pending refund must not appear as settled repayment.

Alternative review paths (C22/A13): staff or owner may reject a requested return or cancel a requested/approved return, recording a review reason. Approval cannot subsequently become rejection; cancel the approved return instead. A received return cannot be cancelled or rejected. Repeating the same decision is a no-op; an incompatible status change requires reloading current state.

The customer sees the rejected/cancelled status and review reason through private order access; the transaction also records audit history and queues the corresponding notification. Rejected/cancelled requests no longer reserve return quantities: a new request with a new request key may use the remaining eligible quantity, after subtracting other requested, approved or received commitments. Reusing the old request key recovers the old request rather than creating a new one. Neither rejection nor cancellation changes stock or authorizes/settles a refund. Goods receipt against a rejected/cancelled return is denied; receiving a return still requires approved status and full quantity disposition. Receiving and review serialize on the order, so the losing action must inspect current state before retrying. These clauses describe backend rules; automated assertions for rejection/cancellation, released eligibility and receipt denial have not been mapped in the journey coverage.

## 12. Catalog, content and store configuration

Journeys: C24, M1–M2, M6–M12. Protected owner provisioning → branding/support, locale/timezone/currency, tax, payments, delivery/pickup/shipping and email configuration → email verification → readiness checks → synthetic purchase/payment/fulfillment/refund before launch. Missing requirements must identify the corrective action. Currency locks after the first order. Pause blocks new purchases while existing orders remain actionable. Membership and owner recovery follow the backend authority rules and maintenance guidance.

Create a draft product → add variants/SKUs, images, specifications and translations → organize categories/collections → preview and publish. Reusable options generate selected missing combinations while preserving existing variant identity. Review bulk changes before application; invalid input retains edits and selections. Later edits must preserve historical purchases. Product availability and promotion eligibility feed authoritative quotes; invalid codes or changed prices require explicit review, not silent acceptance.

Maintain navigation, content, policies, branding and translations → inspect their public localized pages and missing/error states. Maintain receiving accounts, tax and checkout policy, regional shipping, pickup locations, schedules/blackouts, local-delivery areas and reward policy through owner-authorized settings. Invalid configuration blocks affected checkout with actionable feedback. Archived/renamed receiving accounts do not redirect accepted payment instructions. Template publishing belongs to section 14.

## 13. Manual orders, inventory and reporting

Journeys: M3, M13, M16, A11, A14. Owner opens manual-order entry → enters customer name/email → selects shipping or local pickup → supplies a shipping address or configured pickup location and required date/time → selects catalog variants, quantities and payment method → submits → inspects the created order and its calculated total. Pickup requires no shipping address and uses ordinary notice, blackout, schedule, capacity and stock rules; unscheduled pickup is allowed when the selected location permits it. Current manual entry has no local-delivery selector, existing-customer picker or separate pre-submission total-review step. Contact details do not establish account ownership. The backend calculates the quote using current catalog prices, tax and shipping rules and creates the order transactionally. Validation retains entered work. Creation does not bypass ordinary receipt, confirmation or fulfillment prerequisites.

An owner starts inventory tracking with a physical count → inspects reservations and movement history → investigates shortages/pending orders → records supported adjustments. Reservations reduce sellable stock; dispatch/handoff consumes stock; cancellation releases eligible unfulfilled holds. A downward count cannot erase existing obligations. Manual review deadlines do not automatically release reservations. Staff and owners may record counts and inspect stock history; only owners may enable or disable tracking. Stale revisions require a fresh count before saving.

Preview product CSV → identify invalid/duplicate rows → select valid changes → apply → retry using preserved identity if interrupted. Product exports preserve importable identifiers. Order exports are read-only; order import is unsupported.

Owner reviews fiscal sales and thresholds → records supported outside-sales adjustments → exports reports/orders for reconciliation. Sales refunds and payout activity remain distinct. Staff may inspect permitted receipt/ledger views and reconcile cash totals; corrections and payouts require owner authority. Stable pagination/export behavior and ledger limitations are described in [merchant operations](merchant-operations.md#ledger-navigation).

## 14. Notifications and audit review

Journeys: M17–M18, A15. Owner configures email delivery → drafts a notification template → previews allowed variables/locales without sending → validates completeness → publishes → inspects immutable history or rolls back. Invalid drafts must not replace the published version. Prepared retries retain their pinned content/provider identity. Live SMS and phone-verification sending remain disabled; configuration/adapters do not establish an available customer send journey.

Staff and owners inspect failed delivery in the daily queue → investigate the related order/event → escalate repair to the owner/operator → retain delivery history. Separately, owners open administrative activity to inspect audit records; staff access is denied. Email failure does not roll back purchase or remove valid private tracking access. SMTP acceptance is not inbox delivery. General messaging remains deferred. See [events](api-events-spec.md), [template management](notification-template-manager.md) and the [maintenance guide](system-maintenance.md) for delivery diagnostics and recovery.

Permission detail for A15/M18: staff and owners inspect failed-delivery work in their permitted queue. Delivery repair is escalated to an owner or deployment operator using the applicable maintenance tool; queue visibility does not imply a retry permission. Administrative activity is a separate owner-only page, with backend enforcement. Owners inspect the available audit records; ordinary staff must be denied access.

## 15. Merchant access and customer service

Staff/customer session separation (C13–C14/A17): backend sign-in establishes only a staff session, and storefront sign-in establishes only a customer session. The same browser may hold both, including for the same user, with independent cookies and persisted session tables. Customer logout leaves staff signed in; staff logout leaves the customer signed in. Customer cookies cannot authorize merchant pages/APIs or owner recovery, and staff cookies do not establish storefront account ownership. User/password credentials remain shared; password reset revokes both realms for that user. Migration 0038 and fresh sign-in are required when upgrading from shared sessions.

Provisioning boundary (M1/M4/A17): admin users are created through trusted commands run in a terminal. There is no public admin registration or merchant add/invite screen. Terminal provisioning must establish the authentication identity and active owner/staff membership before the first admin sign-in. Customer registration alone never grants admin access. The existing Settings membership controls change role/active status or remove an already provisioned membership; they do not create users. Last-active-owner protection applies to role changes, deactivation and removal. Terminal provisioning is the current supported onboarding boundary, not a missing invitation feature. Use the deployment's trusted provisioning procedure; [script documentation](../scripts/README.md) distinguishes demo initialization from operational tooling, and demo seeding is not a general production staff-creation command.

Journeys: A16–A17. A provisioned staff member or owner opens `/admin/login` → signs in → opens the admin workspace. Incorrect credentials keep the user at sign-in with an error. A customer account has no merchant access. When authentication expires, sign in again and reopen the authorized order/task; inspect committed state before retrying a submission whose outcome was lost. Deactivated/deleted membership blocks the next private request even when an authentication session still exists. Authentication recovery does not restore revoked membership; owner lockout follows the trusted owner recovery procedure in M5. Expiry/resume browser coverage remains unmapped. **Implementation gap:** the admin UI has no sign-out control. An accessible merchant sign-out flow that terminates the session and removes private access remains a required outcome; it is not an implemented journey or merely a missing test. Customer account sign-out is a separate existing flow.

Staff or owner opens Customers → searches/paginates verified customer profiles → opens a profile → reviews linked orders and credit context. Switch to Guest order contacts for paginated contact summaries. Empty searches must remain usable. A guest summary is not an account and cannot establish private order ownership. Open the authorized order workspace for support; escalate cancellation, refunds and corrections to the owner. Do not attach guest orders or disclose private customer data solely because a name, email or reference matches. A denied or expired request returns through the access flow above.
