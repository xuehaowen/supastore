Customer storefront localization supports English (`en`) and Simplified Chinese (`zh`) in both applications.

Page/component catalogs are `packages/i18n/src/app/locales/*.json` and `apps/storefront/lib/locales/*.json`. Shared customer copy, API error messages, status labels and US state names live in `packages/i18n/src/locales/*.json`. Both catalog loaders merge those shared resources; `next-intl` receives the same merged messages used by client components. Add UI copy to a catalog rather than embedding bilingual conditionals or English JSX fallbacks.

Shared helpers localize currency with the store's precision, local calendar dates without timezone shifts, status codes, known system-generated credit-activity descriptions, and recognized API/auth errors. Unknown errors use a translated generic retry message instead of exposing provider text. To retain a specific actionable error, add its English protocol message and Chinese translation to the shared error catalog. Status additions need a key in both shared catalogs; unknown statuses have a translated fallback.

Middleware derives the document language from the locale route (or validated recovery locale query), overriding any incoming locale header. A client component also synchronizes document language during navigation because Next.js retains root layouts. Root metadata, error/not-found screens, accessible labels, calendar/state choices and recovery screens use that language. Switching language preserves the current route and query. Recovery requests carry the language into emailed recovery URLs and order redirects.

Merchant-entered product names, variants, descriptions, image descriptions, categories, collection names, policy content, payment instructions and free-text reasons remain merchant content. Existing catalog/policy translations and configured default-language fallback still apply; these changes do not generate translations of merchant content. Browser-native validation/file-picker chrome uses the browser's own language.

Coverage checks enforce matching, nonempty locale keys and interpolation variables, localized errors/statuses, absence of literal English JSX/accessibility copy in customer screens (admin-only variant tools are excluded), and localized visible date labels while permitting raw submission values. Browser tests exercise Chinese account/profile/address, checkout, order/evidence, recovery and missing-page journeys in the main storefront, plus checkout/error/recovery coverage in the separate storefront.

Verified on 2026-10-09: 652 fast tests passed; nine main-storefront and eight separate-storefront production browser journeys passed. Both production builds, TypeScript and ESLint passed. Tests used isolated synthetic databases and accounts. Changes are local; no production data was changed and no deployment was performed.
