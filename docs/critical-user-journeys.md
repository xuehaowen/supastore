# User journey index

These are acceptance scenarios for intended behavior. Keep user experience journeys separate from accounting/concurrency tests. Financial expectations come from [transaction contracts](transaction-contracts.md).

This is the canonical journey index for customers, staff, owners and operators. Detailed steps and exceptions belong in [business workflows](business-workflows.md); implementation limits belong in [system capabilities](system-capabilities.md). Existing IDs are preserved because tests reference them. C means customer, M means merchant/owner, A means daily administration, and O means deployment operator. These IDs supersede the temporary C/S/O numbering used in conversation.

Actor rules: customers include guests and verified account holders. Active staff can record receipts, confirm orders and fulfill purchases. M journeys require the owner unless the backend explicitly grants the operation to staff. A1–A4 are staff/owner operations, with payout-pending allocations/actions in A1 visible only to owners; A5–A10 require the owner for cancellation, refund authorization, payout execution or receipt correction. A queue displaying an action does not grant permission. Check [states and authority](business-workflows.md#1-states-and-authority) for authorization rules.

## How to read verification coverage

The coverage references link test sources inspected on 2026-10-15. **B** means related browser assertions exist; **I** means related integration assertions exist; **U** means related unit assertions exist. References are partial coverage, not certification of every acceptance clause. No tests were run for these documentation updates. Track implementation gaps separately from verification gaps: an absent user control or flow is not merely an untested feature. Track three independent verification gaps: **automation gap** (an acceptance assertion has no identified automated test), **manual evidence pending** (a human/operational exercise has no attached result), and **provider acceptance pending** (configured external services need acceptance evidence). An unidentified test is not proof that no test exists. A journey is verified only for the build, environment and assertions actually exercised; attach dated results before claiming completion.

| A8  | Uncertain or incorrect payout  | Lost response leaves claim blocked; actual wrong-destination/excess payout opens a discrepancy hold; owner records actual movement and reviewed resolution before replacement; customer entitlement and merchant payout-error loss remain distinct |

### Manual pickup implementation evidence (2026-10-15)

The complete integration run was 123/124: `admin-operations.test.ts` failed `paginates fulfillment and opens orders outside the selected page` (expected 50 rows, received zero). An additional unit selection hit a failure in `admin-request-validation.test.ts` for required carrier validation, outside the modified pickup path. Neither failure is treated as a pass. New scheduled/unscheduled [pickup browser scenarios](../tests/browser/admin-management.spec.ts) could not execute because Next config loading failed with `ERR_SWC_NATIVE_CACHE` from the local native binding cache permissions.
